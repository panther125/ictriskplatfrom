## 一、这套平台解决什么问题

传统风控策略写死在 Java 代码里，导致三个死结：

1. **改一条阈值要发一次版** —— 风控的时效性要求是分钟级，研发排期是周级。
2. **数据接入靠开发写 DAO** —— 每接一个外数源就是一轮开发，字段口径散落在各个 Service 里。
3. **策略不可验证、不可回溯** —— 上线前后无法预演，出事后无法复现"当时为什么拒了这笔"。

本平台把 **取数 → 加工 → 决策** 这条链条三层解耦，全部配置化：

```
视图（View）        特征（Feature）           决策（Strategy）
数据从哪来          数字怎么算                结论怎么出
─────────────────────────────────────────────────────────────
MySQL / CSV / HTTP  │  基础特征（1:1 映射）  │  Workflow 编排
/PMML 等数据源      │  衍生特征（SQL/Java/   │  ├ 分支节点
                    │            Python/算子）│  ├ 决策节点（规则集）
                    │                        │  ├ 决策树节点
                    │                        │  └ 交叉决策树节点
```

业务人员不写代码即可上线策略；研发只维护引擎、适配器和算子库。

## 三、关键设计结论（速览）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 架构风格 | 元数据服务单体（模块化分包）+ 独立无状态执行引擎 + 异步 Worker | 配置台是低频读写，单体足够；引擎是高频只读，必须独立伸缩 |
| 配置存储 | MySQL 存元数据；图/树/矩阵以 **JSON 快照**存储，血缘边冗余到关系表 | 图结构用关系表拆存储读写都痛苦；血缘需要 SQL 查询能力，必须落关系表 |
| 版本模型 | 草稿可改，**发布即不可变快照（Bundle）** | 运行时永不读到半成品配置，回滚 = 切指针 |
| 变量体系 | 全局统一变量池 + 命名空间（`param / view / feat / var / node / sys`） | 三层模块通过变量池解耦，决策层无需知道特征怎么算出来的 |
| 表达式引擎 | AviatorScript（条件/分支/脚本） + Apache Calcite（SQL 特征解析与执行） | Aviator 轻量、无反射依赖、沙箱友好、性能好；Calcite 能给出真正的 SQL 类型推导与 AST 校验 |
| Java 特征沙箱 | Janino 编译 + 独立 ClassLoader + AST 黑名单扫描 | 编译期拦截比运行期拦截可靠；无第三方 jar 依赖 |
| Python 特征 | 独立 `python-runner` 服务（池化进程 + REST/gRPC） | GraalPy 包兼容性差、JEP 与 JVM 生命周期耦合，独立进程隔离性最好 |
| 交叉决策树 | **统一编译成规则集（决策表）执行**，矩阵只是配置态视图 | 引擎只需一种执行原语，性能可控，配置形态可以随便演进 |
| 多租户 | 共享库共享表 + `tenant_id` 全链路透传 + 行级隔离 + 租户级缓存/连接池隔离 | SaaS 成本最优；隔离点集中在框架层，业务代码无感 |
| 前端画布 | AntV X6（或 LogicFlow）+ 自研节点渲染 | 国产方案、节点定制成本低、DAG 布局（dagre）开箱可用 |

## 四、核心假设（评审时请重点确认）

| 编号 | 假设 | 影响 |
|---|---|---|
| A1 | 在线决策为**同步短时**调用，单笔耗时预算 200ms 量级 | 决定引擎线程模型与超时设计 |
| A2 | 决策入参中已有可定位主键（如 userId / applyId），视图按主键查 | 决定视图的 SINGLE 取数模型 |
| A3 | 外数（HTTP 视图）延迟不可控，需熔断降级，不承诺强一致 | 决定降级链设计 |
| A4 | Python 特征在 P1 交付，且 P1 阶段以离线/准实时为主，在线需显式标注风险 | 决定 python-runner 的交付节奏 |
| A5 | 无跨租户数据共享需求（含字典、分箱组件） | 决定元数据隔离粒度 |
| A6 | 决策日志量级在千万~亿级/年，可接受按时间分表 + 冷热分离 | 决定日志存储方案 |

## 五、开放问题（待你确认后我会补进对应章节）

1. **外部决策调用**：是否需要"调用另一个风控系统/模型服务"作为节点？（当前设计为通用 HTTP 动作节点，若有明确对接方可以固化协议）
2. **额度/定价类输出**：决策是否要输出连续值建议（额度、利率），还是仅结论枚举？影响结论模型设计。
3. **实时特征**：是否有 Kafka/Flink 流式特征需求？当前放在 P2。
4. **审批流**：发布是否需要多级审批？SaaS 下是否需要租户自定义审批链？
5. **存量迁移**：是否有现存硬编码策略需要批量导入？如果需要，要额外设计"代码扫描 → 规则生成"的迁移工具。
6. **性能目标精确值**：单实例 QPS 期望值、P99 延迟硬指标，请给一个业务口径（如"峰值 5000 TPS，P99 ≤ 150ms"）。
