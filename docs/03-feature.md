# 03 特征模块设计

## 1. 定位

**特征（Feature）= 决策可用的、有明确业务口径的变量。**

特征层是"业务语言"与"数据语言"之间的翻译层：视图给的是 `overdue_cnt`（技术列名），决策想看到的是 `user_overdue_level`（业务概念）。特征模块的价值就在这个翻译上——**它定义了"什么算高逾期"，并且让所有策略共用同一个口径。**

```
视图层（数据在哪）  ──▶  特征层（口径是什么、怎么算）  ──▶  决策层（什么条件出什么结论）
  技术字段                业务语义 + 计算方法               规则与结论
```

## 2. 特征分类

| | 基础特征 BaseFeature | 衍生特征 DerivedFeature |
|---|---|---|
| 定义 | 对视图字段的 **1:1 引用** | 通过 **SQL / Java / Python / 算子** 加工产出 |
| 允许加工 | ❌ 严格禁止 | ✅ |
| 输入 | 1 个视图字段 | N 个上游特征 + N 个视图字段 + 策略入参 + 常量 |
| 创建成本 | 极低（点选即建） | 中（需要写或配计算逻辑） |
| 主要作用 | 语义化包装、口径收敛、权限与血缘载体 | 真正产生业务价值 |
| 变更影响 | 视图字段变则特征变 | 逻辑变则特征变 |

> **为什么基础特征必须"不能加工"？**
> 因为它的价值不是计算，是**命名与治理**。一旦允许加工，它就和衍生特征没有边界，用户会开始在基础特征上写表达式，最后所有逻辑散落在几百个特征里，血缘图退化成一团。**保持基础特征"纯引用"，才能保证"特征 → 视图字段"的血缘是确定可验证的。**

## 3. 基础特征

### 3.1 元模型

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `featureCode` | string(64) | ✅ | 租户内唯一，`^[a-z][a-z0-9_]{2,63}$`，创建后不可改 |
| `featureName` | string(128) | ✅ | 中文名，如"近 30 天逾期次数" |
| `featureType` | enum | ✅ | 固定 `BASE` |
| `viewRef` | object | ✅ | `{viewCode, viewVersion(可选，默认跟随最新), fieldCode}` |
| `dataType` | enum | ✅ | **继承视图字段类型，不允许强制转换** |
| `defaultValue` | string | | 缺失时的填充值 |
| `missingPolicy` | enum | ✅ | 缺失处理策略，见 §3.3 |
| `required` | boolean | | 是否必填（必填缺失 → 决策中断） |
| `unit` | string | | 单位 |
| `bizDefinition` | text | ✅ | **业务口径说明，必填**。写清楚"这个数从哪来、什么时间范围、含不含某类记录" |
| `tags` | string[] | | 供检索与批量操作 |
| `owner` | userId | ✅ | 责任人 |
| `sensitivity` | enum | | 默认继承视图字段 |
| `status` | enum | | `DRAFT` / `ONLINE` / `OFFLINE` |

### 3.2 硬性约束（保存时校验）

| 编号 | 约束 | 违反时的提示 |
|---|---|---|
| C1 | 只能引用**一个**视图的**一个**字段 | "基础特征不支持多字段" |
| C2 | 不允许任何表达式/算子/函数 | 配置台不提供该入口 |
| C3 | 数据类型必须与视图字段**完全一致** | "如需类型转换，请创建衍生特征" |
| C4 | 视图 `outputShape=LIST` 时，其字段**禁止**建基础特征 | "该视图返回多行，请创建聚合类衍生特征" |
| C5 | 视图字段 `fieldCode` 被删除/改名时，引用它的基础特征**自动置为不可用状态** | 影响面告警 + 阻断视图发布 |
| C6 | `bizDefinition` 不能为空，且长度 ≥ 10 字 | "口径说明是特征治理的基础，请补充" |
| C7 | 命名须符合 `{domain}_{entity}_{metric}[_{window}]` 规范 | 见 §6.1 |

### 3.3 缺失值策略（missingPolicy）

| 策略 | 取值 | 行为 |
|---|---|---|
| `DEFAULT` | `defaultValue` | null → 默认值（推荐用于计数类，默认 0） |
| `PASS_NULL` | — | 保持 null 向下传递，由决策层处理 |
| `ERROR_ABORT` | — | 缺失 → 中断决策，走兜底结论（强依赖场景） |
| `ERROR_CONTINUE` | 原因码 | 缺失 → 记原因码 + 用默认值继续（**风控常用**：既不阻断，也让结果可解释） |

> **`ERROR_CONTINUE` 是风控场景最常用的策略**：数据缺失不应该让一笔正常业务卡住，但必须在决策结果里留下痕迹（原因码 `FEATURE_MISSING_user_overdue_cnt`），便于事后分析"有多少笔是因为数据缺失而走了保守分支"。

### 4.2 InputRef（输入引用）

| 来源 | 语法 | 说明 |
|---|---|---|
| 上游特征 | `feat.user_overdue_cnt` | 可引用基础或衍生特征（形成特征 DAG） |
| 视图字段 | `view.risk_user_info.mobile` | **快捷方式**：无需先建基础特征，直接引视图字段（引擎自动补齐取数依赖） |
| 决策入参 | `param.applyAmount` | 请求入参 |
| 系统变量 | `sys.now`、`sys.channel` | 平台内置 |
| 常量 | 直接在脚本里写 | |

> **设计取舍：为什么允许衍生特征直接引视图字段？**
> 严格分层会说"必须经基础特征"。但实际使用中，一个只用一次的技术字段（如 `create_time`）建基础特征纯属噪音。折中方案：**允许直接引用，但平台在血缘上仍记录到字段级**，并给出提示"建议为高频使用字段创建基础特征"。既能干，也能治理。

> **实现现状（见 [09-feature-base-derived.md](09-feature-base-derived.md)）**：配置台已落地基础特征 / 衍生特征两条创建分支。
> 基础特征为「视图 → 出参」的 1:1 引用（C1–C6 全部在服务端校验），验证时直接复用该视图登记的入参；
> 衍生特征当前采用 **`@@基础特征编码`** 的引用写法，验证时会自动解析所有 `@@` 引用并把被引用基础特征的入参合并去重后带出。
> 上表的 `view.xxx` 直接引视图字段方式尚未实现。

> **特征验证（列表态）**：特征列表的操作列提供「验证」按钮，**已发布上线（PUBLISHED）的特征同样可验证**——
> 验证是只读试跑，不修改口径、不落库，仅把执行结论回写 `verify_status`；如需改动口径仍须先「下线」。
> 口径：基础特征真实执行绑定视图的取数脚本（复用 `POST /views/validate`，只核对特征选定的出参）；
> 衍生特征先解析 `@@` 引用、再用同一组测试值跑被引用基础特征所在视图做取值核对，**表达式本身由引擎在运行时执行**
> （接口返回 `simulated=true`，前端会明确标注）。相关接口：`GET /features/{id}/resolved-inputs`、`POST /features/{id}/trial`。

### 4.3 SQL 衍生特征

#### 执行模型

平台把所有输入**物化成一张内存输入表** `t_input`，用户对这个表写 SQL：

```sql
-- 输入：feat.user_overdue_cnt, feat.user_apply_cnt_7d, param.applyAmount
SELECT
    CASE
        WHEN user_overdue_cnt >= 3 THEN 'H'
        WHEN user_overdue_cnt >= 1 THEN 'M'
        ELSE 'L'
    END AS result
FROM t_input
```

#### 多行输入的处理（关键能力）

当输入包含 LIST 视图字段时，引擎把多行数据物化成独立临时表，支持 join：

```sql
-- 输入：view.loan_order.order_amount (LIST), feat.user_overdue_cnt
SELECT
    COUNT(*)                          AS apply_cnt_30d,
    SUM(order_amount)                 AS apply_amt_30d,
    MAX(order_amount)                 AS max_amt_30d
FROM t_view_loan_order
WHERE create_time >= :window_start
```

| 能力 | 说明 |
|---|---|
| 表名规则 | `t_input`（单行输入）+ `t_view_{viewCode}`（多行视图数据） |
| 聚合函数 | `COUNT / SUM / AVG / MAX / MIN / STDDEV / PERCENTILE / COLLECT_LIST / DISTINCT_COUNT` |
| 窗口过滤 | 内置时间变量 `:window_start` / `:window_end`（由特征参数或系统时间决定） |
| 关联 | 支持 `JOIN` 多个 `t_view_*` 表（同一主键维度） |
| CTE / 子查询 | 支持 |
| 结果集 | P0 要求返回**单行单列**，别名必须是 `result`；`SELECT` 多列在 P1 支持 |

#### 校验与安全

| 项 | 措施 |
|---|---|
| 语法解析 | Apache Calcite 解析成 AST，失败则给出精确位置错误 |
| 结构校验 | 根节点必须是 `SELECT`；禁止 `INSERT/UPDATE/DELETE/DDL`；禁止多语句 |
| 列名校验 | 引用的列必须存在于 `inputs` 声明的清单中，否则报错并提示"补充输入" |
| 类型推导 | Calcite 推导输出类型，与 `outputType` 声明比对 |
| 确定性校验 | 禁止 `RAND()`、`NOW()`、`CURRENT_TIMESTAMP` 等非确定性函数（时间统一用 `:window_*` 或 `sys.now`） |
| 性能校验 | P1：AST 层面识别笛卡尔积、无过滤的全表扫描并告警 |

#### 在线执行方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Calcite 内存执行（Enumerable） | 与校验共用一套 AST，语义一致；支持完整 SQL | 每次执行有规划开销（μs~ms 级） | **P0 主方案** |
| 编译成表达式 / 字节码 | 无规划开销，最快 | 只支持简单表达式，复杂聚合退化严重 | P1 优化路径（"简单表达式直译"快捷键） |
| 拼接 SQL 到目标库执行 | 无内存开销，能用上数据库能力 | 强耦合数据源、延迟高、不安全 | 不采用 |

**推荐组合策略**：编译期判断 SQL 复杂度——
- 无 `FROM` 之外的表引用、无聚合、无子查询 → 直接编译为 Aviator 表达式（纳秒级）
- 其余 → Calcite 内存执行，Plan 缓存复用

> **实现现状（见 [10-feature-engines.md](10-feature-engines.md) §3）**：Calcite 内存执行已落地——入参物化为**单行 `t_input` 表**，
> 平台类型映射 INTEGER/BIGINT/DECIMAL/BOOLEAN/TIMESTAMP/VARCHAR，启用 mysql 函数库，`AS result` 自动改写为 `AS "result"`（Calcite 保留字），
> 启动预热避免首次规划耗时；语法错误、非单列结果、多行结果（取第一行）都有明确回显。
> **多行输入物化 `t_view_*` / JOIN / 聚合与「简单表达式直译」优化本期未实现**；确定性函数检查、列名清单校验以执行期报错替代。

### 4.4 Java 衍生特征

#### 脚本形态

用户实现平台约定接口，只需写方法体：

```java
public static Object apply(Map<String, Object> in, Ctx ctx) {
    int overdueCnt = ((Number) in.get("user_overdue_cnt")).intValue();
    if (overdueCnt >= 3) return "H";
    if (overdueCnt >= 1) return "M";
    return "L";
}
```

#### 沙箱设计（核心）

| 层面 | 措施 |
|---|---|
| **编译** | Janino 编译为字节码；每个特征一个独立 `ClassLoader`，支持热替换（新版本只换 ClassLoader，旧版本自然淘汰） |
| **静态检查** | 编译前用 Javaparser 扫描 AST：① 导入白名单外的类 → 拒绝 ② 出现黑名单符号（`System.exit`、`Runtime`、`Thread`、`File`、`Socket`、`Class.forName`、反射 API） → 拒绝 ③ 出现 `while(true)` 无退出条件 → 告警 |
| **导入白名单** | `java.lang.*`（剔除危险类）、`java.math.*`、`java.time.*`、`java.util.*`（剔除 `Timer`）、`java.util.stream.*`、平台 `rp-common` 的 util 包 |
| **无第三方依赖** | P0 不支持引入任意 jar。P1 提供"特征 SDK 依赖包"上传机制（需审批 + 版本锁定） |
| **运行期** | 独立线程执行 + `timeoutMs` 超时中断（`Future.cancel` 或线程中断）；限制栈深度防递归爆栈（静态检查限制递归调用） |
| **内存** | 无法在 JVM 内做硬限额 → 通过对入参大小限制（`responseSizeLimit` 等）间接约束；异常大的集合操作由超时兜底 |
| **无副作用** | 禁止 IO / 网络 / 线程创建 / 静态可变状态（平台每次调用传入新的 `in` Map 副本） |

> **为什么选 Janino 而不是 Groovy / Nashorn / GraalJS**：
> - Groovy 编译慢（百 ms 级）、运行时重、沙箱难做（大量动态反射逃逸路径）
> - Nashorn 已废弃
> - GraalJS 重、启动慢、需要额外配置
> - **Janino 编译在 10ms 级、运行开销接近原生 Java、生成的字节码可用 ClassLoader 完全隔离**。对于"业务逻辑片段"这个使用场景，复杂度最低、风险最小。

#### 性能

编译一次后缓存 `Class` 对象，调用开销与普通 Java 方法相当（纳秒级）。因此 **Java 特征是在线场景的首选计算方式**（SQL 特征有规划开销，Python 特征有跨进程开销）。

> **实现现状（见 [10-feature-engines.md](10-feature-engines.md) §4）**：Janino 编译执行已落地——支持「只写方法体」（自动包进
> `apply(Map, Ctx)`，编译错误行号换算回用户脚本行号）或「写完整方法」两种写法；每次执行独立 `SimpleCompiler` 天然隔离；
> 危险调用以**正则黑名单**先行拦截（Runtime / ProcessBuilder / System / File / Socket / 反射 / 线程等），
> 与设计稿的「Javaparser AST 白名单扫描」有差距，属 P0 取舍（后续可平滑升级）；
> 超时仅包住 `apply` 调用（编译 10ms 级不设限）；方法签名不符、黑名单命中都有明确中文报错。

### 4.5 Python 衍生特征

#### 脚本形态

```python
def apply(inp: dict, ctx) -> object:
    cnt = inp.get("user_overdue_cnt", 0)
    if cnt >= 3:
        return "H"
    if cnt >= 1:
        return "M"
    return "L"
```

#### 执行方案对比（重要决策）

| 方案 | 隔离性 | 延迟 | 包兼容性 | 运维复杂度 | 结论 |
|---|---|---|---|---|---|
| 独立 `python-runner` 服务（进程池 + REST/gRPC） | ⭐⭐⭐ 进程级隔离 | 1~5ms（RPC + 序列化开销） | ⭐⭐⭐ 完整 CPython | 中（需部署维护） | **推荐** |
| GraalPy 嵌入 JVM | ⭐⭐ | 亚 ms | ⭐ 大量 C 扩展不兼容 | 低 | 不推荐（pandas/numpy 兼容性硬伤） |
| JEP 本地嵌入 CPython | ⭐ | 亚 ms | ⭐⭐⭐ | 高（JVM 崩溃即服务崩溃） | 不推荐 |
| 每次调用起新进程 | ⭐⭐⭐ | 100ms+ | ⭐⭐⭐ | 低 | 仅离线 |

**结论：P1 交付，采用独立 `python-runner` 服务**，架构要点：

```
engine ──HTTP/gRPC──▶ python-runner
                          ├── 进程池（N 个 worker 进程，绕过 GIL）
                          ├── 每个进程预加载指定版本的 Python + 依赖包
                          ├── 脚本缓存（首次执行编译，后续直接调用）
                          └── 超时强制 kill + 进程重建
```

| 设计点 | 说明 |
|---|---|
| 依赖管理 | 平台维护"可用依赖清单"（numpy / pandas / scipy 等，版本锁定）；特征只能使用清单内的包 |
| 版本一致性 | **在线与离线使用同一个 runner 镜像**，依赖版本完全一致 |
| 超时 | runner 侧硬超时（默认 100ms），超时 kill 进程并重建，避免脏状态 |
| 降级 | runner 不可用 → 按 `errorPolicy` 降级，不阻断决策 |
| 在线定位 | **平台在 UI 上显式标注"Python 特征有 ms 级额外开销，建议用于离线/准实时"**，并给出延迟预算提示 |
| 离线执行 | Worker 服务直接调用同一 runner（或本地嵌入 cpythоn），保证语义一致 |

> **实现现状（见 [10-feature-engines.md](10-feature-engines.md) §5）**：独立 `python-runner` 服务已落地
> （`python-runner/runner.py`：FastAPI + 2 常驻工作进程池，JSON Lines 协议，超时 kill 进程并自动重启 + 重试一次，
> 脚本按 sha1 缓存，预置 json/math/re/datetime/decimal/pd/np，`def apply(inp[, ctx])` 单双参自适应）。
> 后端 `PythonRunnerClient` 按 `risk.python-runner.url`（默认 `http://127.0.0.1:8090`）HTTP 调用，危险 import / 动态求值正则黑名单先行拦截；
> **注意 JDK HttpClient 必须固定 HTTP/1.1**（uvicorn 不支持 h2c 升级，否则请求体会丢失报 422）。runner 需**手动启动**，未随后端进程托管。

### 4.6 三种语言的选型指引（配置台内置引导）

| 场景 | 推荐语言 | 理由 |
|---|---|---|
| 简单条件映射、算术、字典查表 | **算子（OP）** | 无需写代码，可视化配置，可读性最好 |
| 聚合、关联、窗口统计 | **SQL** | 表达力天然匹配，Calcite 可校验 |
| 复杂业务逻辑、循环、状态计算 | **Java** | 性能最好，图灵完备 |
| 需要 pandas/numpy/第三方算法库 | **Python** | 生态优势，但注意延迟 |
| 需要调用模型 | 不写代码，用 **PMML 视图** | 模型统一托管，可追溯 |

> **实现现状**：配置台已把四类加工方式做成表达式编辑器的语言页签（`SQL / Java / Python / OP`，切换语言各自保留草稿互不覆盖），
> 每个语言配悬浮帮助卡示例；OP 为可视化规则表编辑器（自动生成 CASE 算子树 JSON，支持「高级 JSON」双向切换）。
> 验证结果会明确标注「表达式真实执行」、引擎标签（如 `Java · Janino 编译执行`）与引擎耗时。四引擎实现细节与浏览器联调结论见
> [10-feature-engines.md](10-feature-engines.md)。

## 5. 可视化算子（OP 类型）

### 5.1 设计目标

让 80% 的常见加工场景**不写代码**即可完成。算子配置本质上是一棵**算子树（DAG）**，最终编译为 SQL 表达式或 Aviator 表达式——与手写衍生特征同构，只是配置方式不同。

### 5.2 算子清单

#### 单值算子

| 分类 | 算子 | 说明 |
|---|---|---|
| 数值 | 绝对值、取整、四舍五入、截断 Clamp、对数、开方、幂、取反、百分比转换 | |
| 字符串 | 截取、拼接、替换、去空格、大小写、长度、正则提取、正则匹配、掩码、URL 编码 | |
| 时间 | 当前时间、日期差、日期加减、提取年月日时分秒、格式化、时间戳转换 | |
| 空值 | 空值判断、空值填充（常量/默认值）、空值置零、Coalesce | |
| 类型 | 转字符串、转数值、转布尔（**显式声明，禁止隐式转换**） | |
| 字典 | 字典映射（code → label）、字典反查、字典分组 | |
| 校验 | 身份证校验、手机号校验、银行卡 Luhn、邮箱校验、统一社会信用代码校验 | |
| 脱敏 | 手机号掩码、身份证掩码、姓名掩码（用于输出字段） | |
| 编码 | MD5 / SHA256 / HMAC（用于对接外数） | |

#### 多值算子

| 算子 | 说明 |
|---|---|
| 四则运算 | `+ - * / %`，金额运算强制 DECIMAL |
| 比较 | `> >= < <= == !=`，输出布尔 |
| 逻辑 | `AND / OR / NOT / IF / CASE WHEN` |
| 极值 | `MAX / MIN / ABS_DIFF` |
| 条件 | 条件表达式（多分支 CASE WHEN 可视化编辑） |

#### 聚合算子（输入为 LIST 视图数据时可用）

| 算子 | 参数 | 输出 |
|---|---|---|
| `COUNT` | 可加过滤条件 | 计数 |
| `SUM` / `AVG` / `MAX` / `MIN` / `STDDEV` | 目标字段 + 过滤条件 | 数值 |
| `DISTINCT_COUNT` | 目标字段 | 去重计数 |
| `TOP_N` | N + 排序字段 + 方向 | 第 N 大的值 |
| `FIRST` / `LAST` | 排序字段 | 首/末条记录的某字段值 |
| `COLLECT` | 目标字段 + 分隔符 | 拼接字符串 |
| `WINDOW_COUNT` | 时间字段 + 窗口期（如 7d/30d）+ 过滤条件 | 窗口内计数 |
| `TREND` | 时间字段 + 周期数 | 环比/趋势（P1） |

#### 分箱算子（供交叉决策树复用）

| 分箱类型 | 说明 |
|---|---|
| 等宽分箱 | 按区间宽度均分（`[0,100) 每 20 一段`） |
| 等频分箱 | 按样本分位点均分（需离线统计分位点后固化） |
| 自定义区间 | 手工配置边界，支持左闭右开语义 |
| 枚举分组 | 按字典/枚举值分组到标签 |
| 表达式分箱 | 每个箱一个条件表达式（最灵活） |
| 缺失箱 | 显式定义 null/异常值的归属箱（**必填**） |

### 5.3 算子树的编辑体验

```
user_overdue_cnt ──▶ [窗口过滤: 近30天] ──▶ [COUNT] ──▶ [分箱: 自定义 3 段] ──▶ result
                                                            │
                                          [字典映射] ──▶ user_overdue_level
```

- 拖拽式节点连线，每个算子节点双击配置参数
- 实时预览：每个中间节点显示样例值（用试算样本驱动）
- 算子树 → 表达式：提供"查看生成的 SQL / 表达式"（可读性 + 可调试）
- 支持"转换成手写 SQL 特征"（一键降级为 SQL 编辑模式，便于处理算子覆盖不到的场景）

## 6. 特征治理

### 6.1 命名规范（强制）

```
{domain}_{entity}_{metric}[_{window}]

示例：
  user_loan_apply_cnt_7d      用户 借款申请 次数 近7天
  device_risk_score           设备 风险分
  order_amt_sum_30d           订单 金额 求和 近30天
  user_overdue_level          用户 逾期 等级（无窗口 = 快照值）

domain : user / device / order / merchant / account / ip / ...
metric : 语义化的度量名，禁止 cnt1 / num / val 这类无语义命名
window : 1d / 7d / 30d / 90d / all / 无（快照）
```

校验规则：正则 + 黑名单（`test`、`tmp`、`temp`、`new`、`copy`、数字后缀）。

### 6.2 标签体系

| 标签类型 | 示例 | 用途 |
|---|---|---|
| 业务域 | `credit` / `payment` / `marketing` | 权限隔离、检索 |
| 特征类别 | `identity` / `behavior` / `credit_history` / `device` / `model_score` | 检索 |
| 数据来源 | `internal` / `external_xxx` / `derived` | 成本分析 |
| 生命周期 | `experimental` / `stable` / `deprecated` | 治理 |
| 敏感级别 | `pii` / `sensitive` / `internal` | 脱敏 |

### 6.3 特征生命周期

```
实验 (experimental)
   │ 试算验证 + 回放效果评估
   ▼
稳定 (stable)  ←─── 被 N 个策略引用
   │ 长期无人引用 / 被替代
   ▼
待废弃 (deprecating)  ── 通知责任人 + 引用方迁移期（如 30 天）
   │
   ▼
已下线 (deprecated)  ── 无法被新策略引用，存量策略仍可运行
```

### 6.4 特征健康度

| 指标 | 说明 |
|---|---|
| 调用量 | 近 7/30 天被调用次数（区分在线/离线） |
| 成功率 / 降级率 | 计算失败与降级的比例 |
| 平均耗时 / P99 | 计算耗时分布 |
| 缓存命中率 | 是否有缓存价值 |
| **空值率** | **在线计算出的 null 比例 —— 超过阈值自动告警**（口径失效的最早信号） |
| **分布漂移** | 近 7 天值分布与历史对比（PSI 简化版），漂移超阈值告警（P1） |
| 引用数 | 被多少个策略/特征引用 |
| 测试用例通过率 | 代码或上游变更后是否仍符合预期 |

> **"空值率"和"分布漂移"是特征治理的核心抓手**：上游表结构变了、字典换了、口径变了，特征值会先用异常的空值率或分布变化表现出来。等业务方投诉"策略结果不对"就已经晚了。平台必须在特征层做这个前哨监控。

## 7. 特征依赖与血缘

### 7.1 依赖 DAG

```
基础特征 ─┐
          ├──▶ 衍生特征 A ──┐
视图字段 ─┘                  ├──▶ 衍生特征 C
基础特征 ─┐                  │
          └──▶ 衍生特征 B ──┘
```

| 规则 | 说明 |
|---|---|
| 允许依赖 | 特征 → 特征（含衍生链）、特征 → 视图字段、特征 → 入参 |
| 禁止 | **环依赖**（保存时 DFS 检测，报错并高亮环路径） |
| 最大深度 | 10 层（超限拒绝，避免执行开销与调试复杂度失控） |
| 跨视图 | 允许（引擎自动把多个视图的取数合并进执行计划） |
| 跨租户 | 禁止 |
| 依赖失效 | 上游特征下线 → 下游标记不可用并阻断发布 |

### 7.2 血缘应用

| 场景 | 能力 |
|---|---|
| 影响面分析 | 视图字段改类型 → 查出所有受影响的特征（含多级衍生）与策略 |
| 根因定位 | 策略结论异常 → 沿血缘反查是哪个特征、哪个视图字段、哪个数据源的问题 |
| 成本分析 | 某个视图的取数成本（外数调用费）可归集到依赖它的策略上 |
| 重复特征发现 | P1：基于脚本签名相似度推荐"可能重复的特征"，治理冗余 |
| 迁移辅助 | 视图下线的迁移清单自动生成 |

## 8. 特征执行模型

### 8.1 批量与去重

一次决策请求内：

```
决策图所有节点声明需要的特征
        │
        ▼
  汇总去重 → 依赖拓扑排序 → 分层并行执行
        │
        ▼
   同一请求内每个特征只算一次（Context 内缓存）
        │
        ▼
   跨请求 TTL 缓存（按 feature 配置，key = tenant + featureCode + version + hash(inputs)）
```

### 8.2 超时与降级

| 层级 | 机制 |
|---|---|
| 特征级超时 | `timeoutMs`（默认 50ms），超时按 `errorPolicy` 处理 |
| 全局预算 | 决策全局 deadline（如 200ms），特征侧感知剩余预算，剩余不足时直接降级不启动 |
| 失败策略 | `DEFAULT_VALUE`（用默认值继续）/ `ABORT`（中断决策）/ `CONTINUE_WITH_CODE`（默认值 + 原因码） |
| 熔断 | 某特征持续失败 → 熔断，短期内直接返回降级值，避免每次都白等超时 |
| 依赖失败传染 | 上游特征降级 → 下游特征用降级值计算（并记录"基于降级值计算"标记，便于事后甄别） |

> **风控安全优先原则**：对于"拒绝类"强依赖特征，`errorPolicy` 应配为 `ABORT` 并走保守兜底结论，而不是"取不到就放行"。平台在 UI 上对默认值做风险提示（如"默认值将导致更宽松的决策，请确认"）。

### 8.3 一致性保证（在线 vs 离线）

| 不一致来源 | 平台对策 |
|---|---|
| 浮点精度 | 金额强制 `DECIMAL`；比率计算统一精度与舍入模式（HALF_UP） |
| 空值语义 | 统一 `null` 传播规则：`null` 参与算术 → `null`；参与比较 → `false`；`null` 参与聚合 → 忽略（`COUNT(*)` 除外，需显式） |
| 时区 | 内部统一 UTC epoch millis；窗口边界统一 `[start, end)` 左闭右开 |
| 字典版本 | 字典随 Bundle 冻结，离线复用同一份 |
| 依赖版本 | 特征/视图版本随 Bundle 冻结 |
| 语言运行时 | Python runner 镜像版本锁定；Java/SQL 同一引擎代码 |
| 数据本身差异 | **无法消除**（在线查的是当前值，离线查的是历史值）→ 平台明确声明"离线回放用于逻辑验证，不用于数据对账" |

**一致性监控（P1）**：抽样同一批样本，在线与离线各跑一次，比对输出差异率，超阈值告警。

## 9. 特征测试

### 9.1 测试用例

| 字段 | 说明 |
|---|---|
| `caseName` | 用例名，如"逾期 3 次应为高风险" |
| `inputs` | 输入值（覆盖多特征） |
| `expectedOutput` | 期望输出（精确值或容差） |
| `expectedReasonCodes` | 期望的原因码（用于验证降级路径） |
| `description` | 用例意图 |

**强制规则**：
- 发布前必须至少有 1 条用例且全部通过
- 上游特征/视图变更后，平台自动重跑所有下游特征的用例，失败则告警（**这是防止"改上游炸下游"的自动化防线**）
- 建议覆盖：正常值、边界值（如阈值 ±1）、空值、异常值（类型错误、超范围）

### 9.2 特征预览

| 模式 | 说明 |
|---|---|
| 手工输入 | 填输入值 → 立即计算 → 展示结果 + 中间步骤（算子树逐步展示各节点值） |
| 从视图取真实数据 | 填业务主键 → 真实取数 → 计算 → 展示（端到端验证） |
| 批量预览 | 上传/粘贴 N 行样本 → 批量计算 → 输出结果表 + 统计（空值率、分布） |
| 对比预览 | 同时跑"当前草稿"与"线上版本"，高亮差异行 |
