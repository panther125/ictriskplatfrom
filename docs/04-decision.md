# 04 决策模块设计

## 1. 定位

**决策模块 = 用 Workflow 图描述"一笔业务应该怎么被判断"。**

它是平台的产品核心：视图和特征都是支撑，最终业务方看到的是这张图，改的是这张图，发布的是这张图。

```
一个策略 = 一张有向无环图（DAG）

  [开始] ─▶ [取数] ─▶ [特征] ─▶ [分支] ─┬─ 条件A ─▶ [决策: 规则集] ─▶ [结束]
                                       ├─ 条件B ─▶ [决策树] ───────▶ [结束]
                                       └─ 默认  ─▶ [交叉决策树] ────▶ [结束]
```

**图不是流程图，是可执行程序。** 每个节点有明确的输入契约、输出契约、失败语义，图本身经过编译期校验后生成执行计划。

## 2. Workflow 图模型

### 2.1 图的构成

| 元素 | 说明 |
|---|---|
| `nodes` | 节点列表，每个节点含类型、配置、位置、通用属性 |
| `edges` | 边列表，连接节点，可带条件与标签 |
| `start` / `end` | 必须有且仅有一个开始节点和一个结束节点 |
| `variables` | 变量池声明（编译期由节点产出推导） |
| `metadata` | 版本、作者、更新时间、变更说明 |

### 2.2 节点通用属性

| 属性 | 说明 |
|---|---|
| `nodeId` | 图内唯一，自动生成（如 `n_001`），用于变量引用 `node.n_001.result` |
| `nodeType` | 节点类型码 |
| `nodeName` | 显示名，建议写业务含义（"逾期准入判断"），会出现在 trace 和决策日志里 |
| `position` | 画布坐标 `{x, y}` |
| `description` | 备注 |
| `timeoutMs` | 节点级超时（覆盖全局） |
| `onError` | 失败策略：`FAIL_FAST`（中断决策）/ `CONTINUE`（跳过继续）/ `DEFAULT_RESULT`（用默认结果继续） |
| `skipWhen` | 跳过条件表达式（满足则跳过本节点），用于条件化执行 |
| `enabled` | 是否启用（停用节点 = 从图中逻辑删除但保留配置，便于灰度调试） |

> **`enabled` 开关是高频需求**：风控经常需要"临时关掉某个校验"。提供开关而不是让用户删节点再重建，能大幅降低操作风险和审计复杂度（停用/启用都会记审计日志）。

## 3. 节点类型清单

| 节点 | 类型码 | 优先级 | 语义 |
|---|---|---|---|
| 开始 | `START` | P0 | 声明决策入参 |
| 取数 | `DATA` | P0 | 拉取视图数据，写入 `view.*` |
| 特征计算 | `FEATURE` | P0 | 计算特征，写入 `feat.*` |
| 条件分支 | `BRANCH` | P0 | 按条件多路分支 |
| 决策 | `DECISION` | P0 | 规则集，输出结论/分数/原因码 |
| 脚本赋值 | `SCRIPT` | P0 | 表达式计算并赋值到 `var.*` |
| 动作 | `ACTION` | P0 | 打标、赋分、设置结论、终止 |
| 子策略 | `SUB_STRATEGY` | P1 | 调用另一个策略（复用/分层治理） |
| 决策树 | `DECISION_TREE` | P1 | 树形结构决策 |
| 交叉决策树 | `CROSS_DECISION_TREE` | P1 | 多维交叉矩阵决策 |
| 并行网关 | `PARALLEL` | P1 | 显式并行执行多个分支后汇聚 |
| 外部调用 | `EXTERNAL_CALL` | P1 | 调用外部决策服务/模型服务 |
| 结束 | `END` | P0 | 组装最终输出 |

> 注：P0 只交付 START / DATA / FEATURE / BRANCH / DECISION / SCRIPT / ACTION / END。DECISION_TREE 与 CROSS_DECISION_TREE 在 P1 交付，但**本设计文档把它们的模型一次设计完整**，避免 P1 时返工底层图模型。

## 4. 上下文变量池（核心机制）

### 4.1 命名空间

| 命名空间 | 写入方 | 示例 | 只读性 |
|---|---|---|---|
| `param.*` | START 节点（来自请求） | `param.userId`、`param.applyAmount` | 全局只读 |
| `view.*` | DATA 节点 | `view.risk_user_info.overdue_cnt` | 全局只读 |
| `feat.*` | FEATURE 节点 | `feat.user_overdue_level` | 全局只读 |
| `var.*` | SCRIPT / ACTION 节点 | `var.totalScore` | 可写 |
| `node.<id>.result` | 各节点产出 | `node.n_005.result.decisionCode` | 全局只读 |
| `sys.*` | 平台注入 | `sys.now`、`sys.requestId`、`sys.tenantId`、`sys.channel` | 全局只读 |

### 4.2 设计要点

**1）强类型 + 编译期推导**
每个变量在编译期有确定类型（来自视图字段类型 / 特征输出类型 / 节点输出契约）。表达式引用变量时做类型检查，`feat.user_overdue_cnt > "abc"` 在保存时就报错，而不是运行时。

**2）支配关系校验（Dominance Check）**
变量引用点必须在其定义点的**所有可能路径的下游**。这是编译期最关键的一项校验：

```
[开始] ─▶ [分支] ─┬─ A ─▶ [决策X 引用 feat.overdue_level]
                  └─ B ─▶ [特征节点 计算 overdue_level]
                          ▲ 错误！路径 A 上 overdue_level 未定义
```

编译期通过**支配树（Dominator Tree）**分析检测此类问题，保存时直接报错并高亮两条路径。**这是防止"运行时空指针"最有效的手段**，也是图模型相对"流程脚本"的核心优势。

**3）表达式只读**
表达式**不允许有副作用**（不能赋值、不能调用有状态函数）。唯一的写入途径是 SCRIPT 节点的显式赋值和 ACTION 节点。这样保证"同一份配置 + 同一份输入 = 同一个输出"，可回放、可缓存。

**4）值拷贝**
写入变量池时做防御性拷贝（或不可变封装），防止节点 A 修改集合影响节点 B 读到的值。

## 5. 边与执行语义

### 5.1 边类型

| 类型 | 说明 |
|---|---|
| `DEFAULT` | 默认边，无条件，最后求值（兜底） |
| `CONDITION` | 带表达式条件的边 |
| `ON_RESULT` | 按上游节点的结果匹配（如 DECISION 节点的结论为 REJECT 时走该边），本质是系统生成的条件边 |

### 5.2 求值规则

```
节点执行完毕 → 取出边列表 → 按 order / priority 升序
   ├─ 依次求值 CONDITION / ON_RESULT 边
   ├─ 第一个为 true 的边 → 走该边继续执行
   ├─ 无匹配 → 走 DEFAULT 边
   └─ 无 DEFAULT 边 → 编译期报错（图必须穷尽）
```

**关键约束**：每个有多条出边的节点，**必须有且仅有一个 DEFAULT 边**（除非该节点是"多路全执行"语义，如 PARALLEL 节点）。编译期强制校验，从根本上杜绝"某笔请求走到图外"的情况。

### 5.3 图的编译期校验清单（保存时执行）

| 校验项 | 说明 | 级别 |
|---|---|---|
| 结构 | 有且仅有一个 START / END；无孤立节点；无环 | ❌ 阻断 |
| 可达性 | 每个节点从 START 可达；每个节点能到达 END | ❌ 阻断 |
| 边穷尽 | 多出边节点必须有 DEFAULT 边 | ❌ 阻断 |
| 除零/短路 | 表达式静态可判定的错误（如字面量除零） | ❌ 阻断 |
| 变量存在 | 引用的变量在命名空间中存在且类型匹配 | ❌ 阻断 |
| 变量支配 | 引用点被定义点支配（见 §4.2） | ❌ 阻断 |
| 必填配置 | 节点必填项完整（如 DECISION 节点至少 1 条规则） | ❌ 阻断 |
| 条件重叠 | 同节点的兄弟条件存在逻辑重叠（可满足性检测） | ⚠️ 警告 |
| 死规则 | 某条件被前面的条件完全覆盖（永远不生效） | ⚠️ 警告 |
| 性能 | 深路径、宽扇出、过多串行取数 | ⚠️ 警告 |
| 口径提示 | 引用了标记为 `experimental` 或 `deprecating` 的特征 | ⚠️ 警告 |
| 缺失兜底 | 引用了 `nullable` 变量但条件里没有空值分支 | ⚠️ 警告 |

> **注意最后两条**：这是把"专家经验"固化进配置台的典型手法。新手常犯的错误（用了实验特征、忘了空值分支）在保存时就被提示，比上线后出事再排查便宜得多。

## 6. 各节点详细设计

### 6.1 START — 入参声明

| 配置 | 说明 |
|---|---|
| `params` | 入参清单：`paramCode`、`dataType`、`required`、`defaultValue`、`validators`、`description` |
| `bizScene` | 业务场景标识（如 `LOAN_APPLY`） |
| `version` | 入参契约版本（对外承诺，变更需通知调用方） |

- 入参是**对外契约**，配置台支持导出接口文档（OpenAPI 片段）
- 新增可选入参 = 兼容变更；删除入参或改类型 = 不兼容变更，**编译期直接阻断发布**除非确认无调用方依赖
- 入参校验失败 → 直接返回参数的失败结论（不进入决策逻辑），错误码明确

### 6.2 DATA — 取数节点

| 配置 | 说明 |
|---|---|
| `viewRefs` | 选 1..N 个视图 |
| `paramBinding` | 每个视图的入参绑定：`视图参数 ← param.xxx / var.xxx / node.xxx.result / 常量` |
| `fieldSelection` | 只取需要的字段（**默认全选，但配置台推荐按需选**，减少内存与缓存开销） |
| `parallel` | 是否并行取数（默认 true） |
| `degradeOnFail` | 单个视图失败时的行为：`CONTINUE_WITH_CODE` / `ABORT` |

- **多个视图并行取数**，共享全局 deadline
- 同数据源的多个视图在 P1 支持下推合并（避免同一数据库 3 次查询）
- 试算时展示每个视图的真实请求与响应（脱敏）、耗时、是否命中缓存

### 6.3 FEATURE — 特征计算节点

| 配置 | 说明 |
|---|---|
| `featureCodes` | 选 1..N 个特征 |
| `paramOverrides` | 覆盖特征的参数（如窗口期） |
| `autoInjectDeps` | 是否自动补齐依赖（推荐的默认行为，见下） |
| `continueOnFail` | 单特征失败是否继续 |

**自动依赖注入**：用户选择 `feat.user_overdue_level` 时，平台自动分析它的依赖链（基础特征 → 视图字段），把需要的视图取数、上游特征计算**自动补进图里**（以可见的节点形式插入，用户可以调整位置）。

```
用户只加了 "逾期等级" 一个特征
        │
        ▼ 平台自动补齐
[DATA: 取 risk_user_info 视图] ─▶ [FEATURE: user_overdue_cnt] ─▶ [FEATURE: user_overdue_level]
```

> **这是"配置化平台好用不好用"的分水岭**。如果每个特征都要用户手工加取数节点，平台会变得极其难用。自动注入 + 可视化可见（而非黑盒），既省事又保持图的可理解性。

**批量**：一次决策中所有 FEATURE 节点声明的特征会**汇总去重后统一批量计算**，不是逐个节点串行执行（编译期融合）。

### 6.4 BRANCH — 条件分支节点

#### 两种模式

**模式 A：条件分支（if / else if / else）**

```
出边列表（按优先级排序）：
  ① feat.user_overdue_level == 'H'                    ──▶ 拒绝流程
  ② feat.user_overdue_level == 'M' && param.amount > 50000  ──▶ 人工审核
  ③ DEFAULT                                            ──▶ 通过流程
```

**模式 B：多路选择（switch on value）**

```
选择变量：feat.device_risk_level
映射：
  'HIGH'       ──▶ 拒绝流程
  'MID'        ──▶ 人工审核
  其他 / null  ──▶ DEFAULT ──▶ 通过流程
```

| 设计点 | 说明 |
|---|---|
| 条件编辑器 | 双形态：① **可视化条件构造器**（变量 + 操作符 + 值，业务人员友好）② **表达式模式**（复杂逻辑） |
| 空值处理 | 可视化模式下强制提供"空值走哪条边"的显式配置 |
| 优先级 | 拖拽调整顺序，顺序即优先级 |
| 互斥提示 | 保存时用 SMT/区间分析做条件重叠初筛，重叠则警告（**不做阻断**，因为重叠有时是业务需要的兜底） |
| 调试 | 试算时高亮命中的出边，未命中的边灰色显示并标注"条件为 false" |

### 6.5 DECISION — 决策节点（规则集）

这是最常用的节点，本质是**一张可执行的规则表**。

#### 结构

| 列 | 说明 |
|---|---|
| 优先级 | 数字越小越先求值，支持拖拽排序 |
| 规则名 | 业务含义说明（会进入日志和原因码文案） |
| 条件 | 表达式 |
| 结论 | `PASS` / `REJECT` / `REVIEW` / `CHALLENGE` / 自定义码 |
| 分数 | 该规则命中的分值（可正可负） |
| 原因码 | 命中后产出的原因码（可多个） |
| 动作 | 命中后的额外动作：打标签、设置 `var.*`、终止决策 |
| 启用 | 单条规则启用/停用 |
| 备注 | 说明、变更历史 |

#### 命中策略（关键配置）

| 策略 | 语义 | 适用场景 |
|---|---|---|
| `FIRST_MATCH` | 第一条命中即返回，后续不再求值 | 规则有序、互斥的场景（**默认**） |
| `HIGHEST_PRIORITY` | 全部求值，取优先级最高的命中 | 规则有序但需要收集全部命中原因 |
| `COLLECT_ALL` | 全部求值，分数累加、原因码全收集，结论按映射表归一 | 评分卡场景 |
| `WEIGHTED_SUM` | 全部求值，加权求和 → 按分数区间映射结论 | 打分决策 |

#### 分数归一

`COLLECT_ALL` / `WEIGHTED_SUM` 策略下，需要配置分数 → 结论的映射：

```
分数区间            结论
[0, 60)             PASS
[60, 80)            REVIEW
[80, +∞)            REJECT
```

配置台用可视化区间段编辑器（可拖拽边界），自动做完备性校验（无缝隙、无重叠、有兜底段）。

#### 输出契约

```
node.<id>.result = {
  decisionCode : "REJECT",
  score        : 85,
  hitRules     : ["R001", "R007"],
  reasonCodes  : [
     {code: "RISK_OVERDUE_HIGH", msg: "近90天逾期{overdue_cnt}次，超过准入阈值", vars: {...}},
     ...
  ],
  evaluatedRules: 12,
  matchedRule   : 1        // FIRST_MATCH 时有效
}
```

#### 配置台交互（重点）

| 能力 | 说明 |
|---|---|
| **Excel 粘贴** | 从 Excel 复制一片单元格直接粘贴到规则表 → 自动解析列与类型（**这是风控人员最高频的操作，必须做好**） |
| 批量操作 | 多选规则 → 批量启用/停用/改结论/改分数/复制/删除 |
| 规则分组 | 按业务含义分组（如"身份核验类"、"多头类"），分组可整体启停、折叠，支持组内排序 |
| 条件模板 | 常用条件存为模板（如"近 N 天 M 次"），一键套用 |
| 规则搜索 | 按条件中的变量/结论/原因码搜索，快速定位 |
| 变更高亮 | 与线上版本对比，新增/修改/删除的规则行高亮（**这是审阅时最有用的功能**） |
| 内联试算 | 在规则表内填入变量值，实时高亮哪条规则会命中 |

### 6.6 SCRIPT — 脚本赋值节点

| 配置 | 说明 |
|---|---|
| `assignments` | 一组赋值：`var.xxx = 表达式` |
| `lang` | 表达式语言（默认 Aviator） |

用途：把复杂表达式的结果提取为中间变量，让后续条件更可读。

```
var.riskScoreBase = feat.user_overdue_cnt * 10 + feat.device_risk_score * 0.5
var.isHighRisk    = var.riskScoreBase >= 80
```

无副作用（只能写 `var.*`，不能改 `feat.*` / `param.*`）。

### 6.7 ACTION — 动作节点

| 动作 | 说明 |
|---|---|
| `SET_DECISION` | 设置最终结论（不终止） |
| `ADD_SCORE` | 累加分数 |
| `ADD_REASON` | 追加原因码 |
| `ADD_TAG` | 打标签到输出（如 `"需二次核验"`） |
| `SET_VAR` | 设置变量 |
| `TERMINATE` | **终止决策**，立即跳到 END 组装结果 |
| `ASSIGN_ROUTE` | 设置路由结果（如"转人工队列A"） |
| `SET_OUTPUT` | 设置自定义输出字段（额度建议、利率等） |

**TERMINATE 的语义细节**：
- 默认**立即短路**，跳过剩余所有节点直接到 END（性能最佳，用于"一票否决"场景）
- 可配置 `collectReasons: true` → 继续执行完剩余节点只为收集原因码，最后统一返回（**用于"给用户完整的拒绝原因"的业务需求**）
- 编译期据此做死代码分析：`TERMINATE` 之后的不可达节点会告警

### 6.8 SUB_STRATEGY — 子策略节点（P1）

| 配置 | 说明 |
|---|---|
| `strategyRef` | 引用的策略（必须是"可复用"标记的策略） |
| `paramMapping` | 入参映射（父 → 子） |
| `outputMapping` | 子策略输出 → 父变量池的映射 |
| `versionPolicy` | `PINNED`（锁定版本，父策略发布时冻结） / `FOLLOW_LATEST`（跟随最新，**不推荐**） |

**为什么需要**：风控常有"基础准入策略"被多个场景复用（贷前、贷中、提额）。复用能保证口径一致，避免同一套规则复制 5 份各自漂移。

**嵌套限制**：最多 3 层，禁止循环引用（编译期检测）。子策略的 trace 会嵌入父的 trace 树，保证可读。

### 6.9 EXTERNAL_CALL — 外部调用节点（P1）

调用外部决策服务/模型服务，把结果作为变量使用。与 HTTP 视图的区别是：它是**决策流程中的动作**（可能需要传当前上下文），而 HTTP 视图是**取数**。P0 阶段可用 HTTP 视图 + 特征节点组合替代。

### 6.10 END — 结束节点

| 配置 | 说明 |
|---|---|
| `outputs` | 输出字段定义：`outputCode`、来源表达式、类型 |
| `decisionSource` | 最终结论来源（哪个节点/变量） |
| `responseTemplate` | 响应组装模板（可选，用于定制响应结构） |

输出示例：

```json
{
  "decisionCode": "REJECT",
  "score": 85,
  "reasonCodes": ["RISK_OVERDUE_HIGH"],
  "route": "REJECT_AUTO",
  "outputs": { "suggestAmount": 0, "riskLevel": "HIGH" }
}
```

## 7. 决策树节点 DECISION_TREE（P1）

### 7.1 结构模型

```
节点（TreeNode）
  ├─ id / parentId
  ├─ 类型：INTERNAL（分裂节点） / LEAF（叶子结论）
  ├─ 分裂条件（INTERNAL）
  ├─ 结论（LEAF）
  └─ 子节点列表

分裂条件类型：
  ① 阈值区间     feat.age：(-∞,18) [18,25) [25,35) [35,45) [45,+∞)
  ② 枚举匹配     feat.device_risk_level IN ('HIGH') / IN ('MID')
  ③ 集合包含     feat.tags CONTAINS 'blacklist'
  ④ 表达式       任意表达式
  ⑤ 缺失分支     feat.age IS NULL
```

### 7.2 设计要点

| 项 | 设计 |
|---|---|
| **可视化** | 树形布局（dagre / 自研分层布局），支持折叠、缩放、拖拽、右侧属性面板 |
| **分裂编辑** | 右键节点 → 选择分裂字段 → 选择分裂方式 → 自动生成子节点（自动带空值分支） |
| **批量操作** | 选中多个叶子 → 批量设置结论；选中子树 → 复制/删除/剪枝 |
| **区间自动生成** | 数值字段选择"等宽分段（N 段）"或"按常用分位点"自动生成区间，再手工微调 |
| **互斥完备校验** | 同层子节点的条件必须互斥（区间不重叠）+ 完备（区间无缝隙 + 有缺失分支 + 有其他兜底）→ **不满足直接阻断保存** |
| **规模限制** | 最大深度 20 层、最多 500 个节点（超出建议拆成多棵树） |
| **样本分布展示** | P1：基于回放数据在每个节点显示样本占比与结论分布（**让业务方一眼看出"这棵树在真实数据上是不是白建"**） |
| **导入导出** | 导出 JSON / 导出规则表 / 导出可视化图片；从规则表反向生成树（P2） |
| **树上调试** | 试算时高亮实际走过的路径，每个分裂节点显示实际取值与判定结果 |

### 7.3 执行语义

从根开始，**按子节点顺序**求值分裂条件，命中第一个满足的子节点向下，直到叶子节点，输出叶子结论（结论码 + 分数 + 原因码 + 动作）。

### 7.4 与「决策节点」的关系

| | DECISION（规则表） | DECISION_TREE（树） |
|---|---|---|
| 适合 | 规则之间相对独立、可排序 | 维度之间有**层级关系**（先看 A，再看 B） |
| 优势 | 规则增删简单 | 逻辑结构清晰，覆盖性好（强制完备） |
| 缺点 | 容易出现规则冲突与遗漏 | 维度多了会爆炸 |
| 建议 | 通用场景首选 | 有明显层级判定逻辑时使用 |

## 8. 交叉决策树节点 CROSS_DECISION_TREE（P1，重点）

### 8.1 业务动机

风控里有大量"**多维组合 → 结论**"的决策，例如：

```
渠道 × 客户等级 × 申请金额段  →  是否需要人工审核
设备风险 × 逾期等级          →  通过 / 人工 / 拒绝
地区 × 产品 × 风险分档        →  额度系数
```

用规则表写：`3 × 4 × 5 = 60` 条规则，每条一行，人根本看不过来，改一个维度要改 20 行。
用决策树写：维度之间有"先后顺序"的暗示，但业务方的真实心智是**平等的矩阵**，树的表达会扭曲。

**交叉决策树的本质是：把 60 条规则的决策表，渲染成一个 3×4×5 的可视化矩阵，让业务方像填 Excel 一样填结论。**

### 8.2 两种配置模式

#### 模式 A：维度交叉矩阵（N 维交叉表）

**维度定义**（有序列表，顺序 = 求值优先级与展示顺序）：

| 维度 | 变量 | 分箱定义 |
|---|---|---|
| D1 渠道 | `param.channel` | 枚举分组：`{线上APP, 微信小程序}` → `ONLINE`；`{线下门店}` → `OFFLINE`；其他 → `OTHER` |
| D2 客户等级 | `feat.user_level` | 枚举：`A/B/C/D` + 缺失 → `UNKNOWN` |
| D3 申请金额 | `param.applyAmount` | 数值区间：`(-∞,1万)` `[1万,5万)` `[5万,20万)` `[20万,+∞)` + 缺失 |
| D4 风险分档 | `feat.risk_score_bin` | 引用分箱组件 `RISK_SCORE_5` |

**单元格 = 结论**：

```
结论结构 = { decisionCode, score, reasonCode, action, 备注 }
```

**渲染策略**：

| 维度数 | 渲染方式 |
|---|---|
| 2 维 | 标准二维表格：行 = D1，列 = D2，单元格可编辑 |
| 3 维 | 表格 + 维度切片：固定 D3 的某个箱，展示 D1×D2 表格，用 Tab 切换 D3（**默认渲染方式**） |
| 4 维及以上 | ① 双 Tab 切片（固定 D3、D4，展示 D1×D2）② 列表模式（每行 = 一个组合 + 结论，支持从 CSV 导入导出） |

**单元格可以是**：

| 类型 | 说明 |
|---|---|
| 具体结论 | 最常见，直接配结论 |
| 引用另一棵树 | 命中该格子后，继续走指定的决策树/子矩阵（**支持组合爆炸的分治**） |
| 引用子策略 | 走另一个完整策略（复用治理） |
| 空（继承默认） | 未配置的格子走 `defaultCell` |

**兜底设计**：
- `defaultCell` 必填（未覆盖的格子走这里）
- 每个维度的分箱必须包含**缺失箱**（`null` 的归属），否则阻断保存
- 配置台实时显示**覆盖率**（已显式配置的格子数 / 总格子数），低于阈值告警

#### 模式 B：双树交叉（Tree × Tree）

**动机**：有些业务方的逻辑天然是两棵树，"规则树"和"评分树"，或者"渠道树"和"风险树"，需要**交叉看**。

| 配置 | 说明 |
|---|---|
| 左树 | 一棵完整的子决策树 |
| 右树 | 一棵完整的子决策树 |
| 交叉结果 | 左叶子 × 右叶子的笛卡尔积矩阵，每个组合配结论 |
| 渲染 | 行 = 左树的叶子（显示叶子路径摘要，如"年龄<25 → 无社保"），列 = 右树的叶子 |
| 叶子摘要 | 悬停/展开显示完整的路径条件，避免"叶子叫什么"的歧义 |
| 子树缺失处理 | 某棵树因数据缺失无法判定 → 走 `fallback`（另一棵树单独决策 / 默认结论），必须显式配置 |
| 子树复用 | 左树/右树可直接引用平台上已有的决策树（被其他策略的树复用） |

**适用判断（配置台内置引导）**：
- 如果两棵树的叶子数乘积 > 400，提示"建议改用维度矩阵或拆分策略"
- 如果两棵树的维度有重叠（都在用同一个变量分裂），提示"可能存在冗余，建议合并为一棵矩阵"

### 8.3 底层统一设计（关键架构决策）

**无论模式 A 还是模式 B，编译期统一编译为「规则集（决策表）」：**

```
模式 A（维度矩阵）
   D1=ONLINE ∧ D2=A ∧ D3=[1万,5万) ∧ D4=档3  →  REVIEW(score=60)
   D1=ONLINE ∧ D2=A ∧ D3=[1万,5万) ∧ D4=档4  →  REJECT(...)
   ...（N1×N2×N3×N4 条规则，未显式配置的格子用 defaultCell 展开）

模式 B（双树交叉）
   左叶L1 条件 ∧ 右叶R1 条件  →  结论
   左叶L1 条件 ∧ 右叶R2 条件  →  结论
   ...（|Leaf(N1)| × |Leaf(N2)| 条规则）
        │
        ▼ 统一产物
   DecisionTable {
     dimensions: [ {code, varRef, boxes: [{boxId, condition, label}]} ... ],
     cells: Map<boxId组合, 结论>,
     defaultCell: 结论,
     lookupStrategy: MULTI_LEVEL_INDEX
   }
```

**为什么统一编译成规则集**：

| 理由 | 说明 |
|---|---|
| 引擎简单 | 执行引擎只需要一种原语（条件求值 + 查表），不需要分别处理树遍历和矩阵查表 |
| 性能可控 | 编译期可以把矩阵结构优化成**多级索引**，避免逐条规则扫描 |
| 配置形态可演进 | 未来要加"三层交叉"、"矩阵叠加"等新形态，只需扩展编译器，引擎零改动 |
| 可反哺 | 规则集可以导出、可以被单测、可以被回放，与其他节点形式一致 |

### 8.4 执行结构（编译产物）

不采用"逐条规则扫描"（矩阵场景规则数可能几百上千条）。编译为**多级索引查找**：

```
DecisionTable {
  // 第 1 维：箱 ID → 第 2 维子表（哈希查找 O(1)）
  level1 : Map<boxIdOfD1, DecisionTable_level2>

  DecisionTable_level2 {
    // 第 2 维：箱 ID → 剩余维度的子表
    level2 : Map<boxIdOfD2, DecisionTable_level3>
    defaultCell : 结论
  }
  ...
  // 最后一维：箱 ID → 结论 直接映射
  leaf : Map<boxIdOfDn, 结论>
  defaultCell : 结论   // 每个层级都有兜底
}
```

查找路径：`D1 取箱 → D2 取箱 → ... → 取结论`，**复杂度 O(维度数)**，与格子总数无关。1000 个格子的矩阵和 4 个格子的矩阵查找开销几乎一样。

**箱位判定（Binner）的实现**：
- 枚举箱：`Map<值, boxId>` 直接查（预构建）
- 区间箱：有序数组 + 二分查找
- 表达式箱：按顺序求值（仅在必要时使用）
- 缺失/异常：统一落到该维度的 `MISSING` / `OTHER` 箱

**编译期优化**：
- 相同结论的相邻格子可合并为一条规则（矩阵 → 规则集压缩，减少体积）
- 大部分格子都走 defaultCell 时，只编译显式差异部分
- 编译产物做校验和，随 Bundle 冻结

### 8.5 分箱器（Binner）组件化

分箱逻辑在风控中会跨策略复用（"风险分 5 档"这个分箱，很多策略都用）。因此：

| 设计 | 说明 |
|---|---|
| **平台级分箱组件** | `BinDef` 独立实体，可被多个交叉树引用 |
| 引用方式 | 交叉树维度配置 `binRef: RISK_SCORE_5` 或就地定义 `inlineBin` |
| 引用版本 | 随 Bundle 冻结；分箱组件升级 = 引用它的策略需重新发布（影响面可查） |
| 分箱类型 | 等宽、等频（需分位点数据）、自定义区间、枚举分组、表达式、字典分组 |
| 边界语义 | **统一左闭右开 `[a, b)`**，平台自动生成边界数组，避免手工配置产生"缝隙/重叠" |
| 缺失与越界 | 强制要求显式配置 `MISSING` / `OTHER` 箱 |
| 测试 | 分箱组件带测试用例（输入值 → 期望箱 ID），发布前必跑 |
| 预览 | 配置分箱时可上传/粘贴一批真实值，平台展示各箱的样本分布（**避免"分箱边界全落在空区间"的低级错误**） |

### 8.6 配置台交互设计（这是产品成败的关键）

一个 3×4×5 = 60 格的矩阵，如果让用户一格一格点，体验是灾难。必须提供：

| 能力 | 说明 |
|---|---|
| **区域框选 + 批量填充** | 鼠标拖拽选中一片格子 → 右侧选择结论 → 一键填充（**最高频操作**） |
| 整行/整列填充 | 点击行头/列头选中整行/整列 → 填充 |
| 键盘操作 | Tab/方向键在格子间移动；数字/字母快捷键直接填结论（如 `1`=通过 `2`=人工 `3`=拒绝） |
| 复制/粘贴 | 支持从 Excel 复制一片区域粘贴进来（**必须支持，业务方习惯在 Excel 里规划矩阵**） |
| 填充柄 | 拖拽单元格右下角向相邻格子复制结论 |
| 导出 CSV | 导出当前矩阵为 CSV（带行列表头）→ 在 Excel 里编辑 → 导回 |
| 颜色语义 | 通过=绿 / 人工=黄 / 拒绝=红 / 未配置=灰；可切换"颜色模式"（按结论 或 按分数热力图） |
| 与线上对比 | 编辑态与线上版本并排/叠加对比，**变化的格子描边高亮 + 变更摘要列表**（"共修改 7 个格子：新增 3，修改 4"） |
| 未配置提醒 | 未配置格子灰底 + 顶部统计"未显式配置 12 格（走默认：人工审核）" |
| 维度管理 | 维度可增删改、调整顺序（顺序影响优先级与展示）、可临时禁用某维度（用于调试） |
| 大矩阵性能 | 虚拟滚动渲染；> 500 格时自动切到"列表模式"并提示 |
| 矩阵导航 | 3 维及以上提供维度切片器（类似数据透视表的筛选器），可"只显示 D3=高额 的切片" |
| 一键转规则表 | 把矩阵展开成规则表查看（便于评审与导出），也可反向从规则表生成矩阵（P2） |
| 试算联动 | 试算时高亮命中的那条路径（哪一行的哪个格），显示每个维度的实际取值与落箱 |
| 撤销重做 | 矩阵编辑必须有完整的 undo/redo（**没有 undo 的矩阵编辑器没人敢用**） |

### 8.7 校验清单（保存时）

| 校验 | 级别 |
|---|---|
| 每个维度至少 2 个箱 | ❌ 阻断 |
| 每个维度的箱互斥（区间无重叠） | ❌ 阻断 |
| 每个维度的箱完备（区间无缝隙）或显式声明"其他归入 MISSING/OTHER" | ❌ 阻断 |
| 每个维度必须有 MISSING 箱 | ❌ 阻断 |
| `defaultCell` 必须配置 | ❌ 阻断 |
| 维度变量类型与分箱类型匹配（数值区间 vs 枚举） | ❌ 阻断 |
| 引用型单元格（引用他树/子策略）的循环引用检测 | ❌ 阻断 |
| 维度数 > 6 或总格子数 > 5000 | ❌ 阻断（提示拆分策略） |
| 覆盖率 < 50% | ⚠️ 警告 |
| 存在整行/整列全部走默认 | ⚠️ 警告（可能是维度配错了） |
| 分箱的某箱样本占比为 0（基于回放样本） | ⚠️ 警告 |

### 8.8 两个模式的选型指引（配置台内置）

| 业务特征 | 推荐 |
|---|---|
| 维度之间平等，都是枚举/分箱值 | 模式 A（维度矩阵） |
| 维度数 2~3 | 模式 A |
| 维度数 4+ | 模式 A + 切片/列表模式 |
| 逻辑天然分两阶段（先粗筛再细分） | 模式 B（双树交叉） |
| 单个维度本身需要多层判定逻辑 | 模式 B，把复杂维度做成树 |
| 需要"格子里有格子"的嵌套决策 | 模式 A + 单元格引用另一棵树 |

### 9.3 类型系统与空值语义

| 规则 | 说明 |
|---|---|
| 编译期类型检查 | 变量类型已知，运算符做类型兼容校验 |
| 隐式转换 | **禁止**。`feat.amount > "100"` 报错，必须显式 `fn.toNumber("100")` |
| 空值比较 | `null == null` → true；`null > 5` → false；`null == 'x'` → false |
| 空值算术 | `null + 1` → null（**不做"null 当 0"的隐式处理**） |
| 空值逻辑 | `null && true` → false；`null \|\| true` → true（三值逻辑简化为二值，`null` 视为 false） |
| 除法 | 除数为 0 → 返回 null + 记原因码（**不抛异常**，风控场景不应因单个计算错误中断） |
| 精度 | 金额/比率运算统一 DECIMAL(20,6)，最终输出按字段声明精度 HALF_UP 舍入 |
| 字符串比较 | 默认区分大小写，提供 `equalsIgnoreCase` |

> **空值语义是决策配置里最容易踩的坑**。平台的处理方式：① 语义明确固化，不留给用户想象空间；② 配置台在条件编辑器里，如果左边变量 `nullable=true` 而没有空值分支，主动给出黄色提示。

│  ✔ START      入参校验通过              0.1ms       │
│  ✔ DATA       取 risk_user_info        32.4ms ⚡缓存命中│
│  ✔ DATA       取 loan_order (LIST, 8行) 45.1ms       │
│  ✔ FEATURE    user_overdue_level=H      2.1ms        │
│  ✔ FEATURE    user_apply_cnt_7d=4       1.8ms        │
│  ✔ BRANCH     命中出边② "中等风险+大额"  0.1ms       │
│  ✔ DECISION   命中 R007 "近7天申请4次"   0.3ms       │
│     └ 结论 REJECT 分数 85                          │
│  ✔ ACTION     TERMINATE（短路，跳过 3 个节点）         │
│  ✔ END        组装输出                  0.1ms        │
│                                                      │
│ 总耗时 82.0ms ｜ 结论 REJECT ｜ 原因码 2 个            │
└─────────────────────────────────────────────────────┘
```

| 能力 | 说明 |
|---|---|
| **逐节点 trace** | 每个节点的输入变量、输出变量、耗时、状态（成功/降级/跳过/失败） |
| **命中高亮** | 分支节点的哪条边被命中、决策节点哪条规则命中、交叉矩阵哪个格子命中 |
| **变量快照** | 任意节点处的完整变量池快照（可切换查看"执行到此处时"的所有变量值） |
| **引用跳转** | 点击变量可跳到它的定义节点；点击特征可跳到特征详情 |
| **副作用提示** | 明确标出哪些节点走了降级/超时，哪些值为默认值 |
| **返回报文** | 展示完整的对外响应 JSON |

### 10.2 试算记录的保存与复用

每次试算可保存为**用例**（输入 + 期望输出 + 备注），形成**回归用例集**。发布前自动跑全量用例，结果与期望不符则阻断发布。这是策略变更的安全网。

### 10.3 批量回放（P1）

| 能力 | 说明 |
|---|---|
| 输入源 | 上传 CSV / 选择历史决策日志（按时间窗口）/ 指定样本表 |
| 执行 | Worker 服务并行执行，不走在线引擎（避免影响线上） |
| 输出明细 | 每笔的完整结果 + 命中路径 + 关键变量值（可下载 CSV） |
| 统计报告 | 总数、通过/拒绝/人工占比、原因码 TOP N、各节点耗时分布、特征空值率、降级率 |
| **新旧对比** | 同一批样本跑两个版本，输出差异分析：结论变化量、变化分布、"旧通过新拒绝"与"旧拒绝新通过"的样本明细（**风控最关心这两个方向**） |
| **阈值扫描** | 选择某个阈值变量，扫描一段区间（如分数阈值 60~90），输出各阈值下的通过率/预估坏账率曲线（P2） |
| 大任务控制 | 样本量上限、并发上限、任务排队、可取消 |

### 10.4 影子模式（P1）

线上真实流量同时跑新旧两个版本，**只返回旧版本结果**（不影响业务），记录差异。

| 用途 | 说明 |
|---|---|
| 安全性验证 | 观察新版本在真实分布上的表现，无风险 |
| 差异归因 | 对差异样本做归因分析（因为哪个特征/哪条规则变了） |
| 灰度前置 | 影子跑一段时间无异常后再正式灰度 |

## 11. 版本、发布与灰度

### 11.1 状态机

```
  DRAFT ──提交──▶ TESTING ──提交审批──▶ PENDING_APPROVAL ──审批通过──▶ RELEASED
    ▲                │                        │                          │
    │                │ 打回                    │ 驳回                     │ 灰度中
    └────────────────┴────────────────────────┘                          │
                                                                          ▼
                                                                    FULL_RELEASE
                                                                          │
                                                                          ▼
                                                                      DEPRECATED
                    回滚 = 把 RELEASED 指针切到任意历史版本
```

### 11.2 Bundle 快照（核心机制）

发布时构建不可变快照，包含：

| 内容 | 说明 |
|---|---|
| 策略图 | `graph_json` 全量 |
| 特征定义 | 所有被引用特征的**当次版本**的完整定义（含脚本、输入清单） |
| 视图定义 | 所有被引用视图的当次版本（含连接引用、取数逻辑、字段定义） |
| 分箱/字典 | 被引用的分箱组件与字典的当次版本 |
| 子策略 | 被引用子策略的当次版本（PINNED 模式下） |
| 元信息 | 构建时间、构建人、校验和（SHA-256）、依赖清单 |

```
Bundle {
  bundleId, strategyCode, version, tenantId,
  graph: {...},
  features: [{code, version, lang, script, inputs, ...}],
  views: [{code, version, type, typeConfig, fields, ...}],
  bins: [...], dicts: [...],
  checksum: "sha256:...",
  builtAt, builtBy
}
```

**运行时只认 Bundle。** 修改任何被引用的特征，都必须重新发布策略才能生效——这是"防止上游变更炸下游"的根本保障，也让"线上究竟在跑什么"永远有确定答案。

### 11.3 灰度

| 灰度方式 | 说明 |
|---|---|
| 百分比 | `hash(bizKey) % 100 < percent`，**同一 bizKey 稳定命中同一版本**（不抖动） |
| 白名单 | 指定 userId / 订单号列表 |
| 渠道 | 按 `param.channel` 等入参字段路由 |
| 标签 | 按入参中的标签路由 |
| 组合 | 多条件 AND/OR 组合 |

**灰度约束**：
- 同时最多 5 个活跃版本（防止版本碎片化）
- 灰度自动推进（可配置：观察 N 小时无异常 → 自动提升百分比）
- 灰度期间实时监控指标（结论分布对比、错误率、耗时），异常自动回滚（P1）

### 11.4 版本对比（Diff）

| 对比维度 | 展示方式 |
|---|---|
| 图结构 | 节点增删改列表 + 画布上差异高亮（新增绿、删除红、修改黄） |
| 节点配置 | 逐字段 diff（如"决策节点 R007 的分数 80 → 85"） |
| 表达式 | 字符串级 diff 高亮 |
| 交叉矩阵 | **单元格级 diff**：变化的格子描边 + 汇总"共修改 7 格" |
| 依赖变化 | 引用的特征/视图版本变化列表 |
| 影响预估 | 基于回放样本的结论变化率（P1） |

### 11.5 审批

| 项 | 说明 |
|---|---|
| 审批模式 | 可配：无审批 / 单人审批 / 双人审批 / 按角色审批 |
| 审批内容 | 版本 diff + 试算报告 + 回放报告（如果跑过）作为附件 |
| 审批留痕 | 审批人、时间、意见，永久保留 |
| 紧急通道 | P1：支持"紧急发布"（需更高权限 + 强制事后复核 + 强告警） |

## 12. 前端编排器设计

### 12.1 界面布局

```
┌──────────────────────────────────────────────────────────────────────────┐
│ [策略名 v3 草稿]  [保存] [试算] [对比] [提交审批] [发布]     ● 校验通过(2警告) │
├────────┬────────────────────────────────────────────────┬────────────────┤
│        │                                                │                │

│ ○ 取数  │    [开始]──▶[取数]──▶[特征]──▶[分支]──┬─▶...    │  节点名:       │
│ ○ 特征  │                                  │        │  逾期准入判断   │
│ ○ 分支  │                                  └─▶...    │                │
│ ○ 决策  │                                                │  条件:         │
│ ○ 决策树 │         (DAG 自动布局 + 手工微调)               │  ...           │
│ ○ 交叉树 │                                                │                │

│        │                                                │  [试算此节点]   │
├────────┴────────────────────────────────────────────────┴────────────────┤

### 12.2 画布能力

| 能力 | 说明 |
|---|---|
| 布局 | dagre 自动分层布局；支持切换为手工模式；一键"重新布局" |
| 导航 | 缩放、平移、小地图、缩放到适配、搜索并定位节点 |
| 编辑 | 框选、多选、复制粘贴（支持跨策略复制子图）、删除、对齐辅助线、网格吸附 |
| 撤销重做 | 完整 undo/redo 栈（**必须有**，编排器没有 undo 等于没有编辑器） |
| 连线 | 从节点端口拖出连线；连线时实时校验（禁止成环、禁止非法连接并给出原因） |
| 折叠 | 折叠子图/分组，隐藏细节（大策略必备） |
| 分组 | 把一批节点框成业务分组（"身份核验区"、"额度决策区"），带颜色与标题 |
| 节点状态 | 节点上显示：状态图标（草稿/有错误）、试算耗时、命中次数（灰度期） |
| 快捷操作 | 右键菜单（试算此节点、复制、停用、查看引用、跳转到特征） |
| 只看路径 | 试算后"只高亮实际路径"，其余节点淡出 |

### 12.3 变量选择器（统一组件）

所有需要写变量的地方（条件、表达式、脚本、入参绑定），都提供统一的变量选择器：

```
[🔍 输入关键词...]
─────────────────────────────
📋 入参 (3)
   param.userId            STRING
   param.applyAmount       DECIMAL
⚙ 特征 (12)  [按标签筛选 ▼]
   feat.user_overdue_level   STRING  ← 近90天逾期等级
   feat.user_apply_cnt_7d    BIGINT  ← 近7天申请次数
📦 视图字段 (8)
   view.risk_user_info.mobile  STRING (PII)
🔧 中间变量 (2)
   var.riskScoreBase        DECIMAL
🔗 节点结果 (4)
   node.n_005.result.decisionCode  STRING
─────────────────────────────
提示：显示每个变量的类型、口径说明、敏感级别
```

**关键**：显示变量的**业务口径说明**而不只是变量名。用户看到"近 90 天逾期等级"才知道该不该用。

| 操作 | 只读 | 策略开发 | 策略审批 | 管理员 |
|---|---|---|---|---|
| 查看策略/图/试算记录 | ✅ | ✅ | ✅ | ✅ |
| 编辑草稿 / 试算 | ❌ | ✅ | ✅ | ✅ |
| 提交审批 | ❌ | ✅ | ✅ | ✅ |
| 审批通过 / 驳回 | ❌ | ❌ | ✅ | ✅ |
| 发布 / 回滚 | ❌ | ❌ | ✅ | ✅ |
| 强制下线 / 删除策略 | ❌ | ❌ | ❌ | ✅ |

## 13. 本章待确认项

- [ ] §8.2 模式 A 在 4 维以上时，切片 + 列表模式的体验需要原型验证。是否有 5 维以上的真实业务场景？如果有，可能需要更激进的方案（如"矩阵模板 + 例外规则"）。
- [ ] §8.6 矩阵编辑器的工作量不小（框选填充、Excel 粘贴、undo/redo、diff 高亮），需要前端排期充分。是否需要先做简版（表格 + 批量填充）再迭代？
- [ ] §9.2 自定义函数是否需要支持租户上传 Java 实现？如果是 SaaS，沙箱与安全审查成本较高，建议 P2。
- [ ] §11.5 审批流的具体形态：SaaS 下是平台统一流程，还是租户可自定义审批链？后者需要引入工作流引擎（如 Flowable），成本显著上升。
- [ ] §12.2 是否需要"策略模板市场"（预置常见风控策略模板，租户一键复制后修改）？这对 SaaS 获客价值较大，但属于 P2。
- [ ] 未设计：**策略间冲突检测**（多个策略对同一笔业务的结论是否需要一致性校验？）如果调用方会同时调用多个策略并做合并，需要在文档中补充"多策略合并规则"。
